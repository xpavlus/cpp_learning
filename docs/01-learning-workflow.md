# 01 — Как вести уроки в репозитории

Этот документ описывает рабочий процесс обучения: как начинать тему, делать задания, использовать git и получать ревью.

## Цель процесса

Репозиторий должен быть не только набором файлов с кодом, но и журналом обучения.

Хороший урок оставляет после себя:

- рабочий код;
- понятную историю коммитов;
- заметки о том, что было сложно;
- исправления после ревью;
- ясное понимание, что тема действительно закреплена.

## Базовый цикл урока

Каждая тема проходит один и тот же цикл:

| Шаг | Действие | Результат |
|-----|----------|-----------|
| 1 | Прочитать `notes.md` | Понимание темы на уровне идей и синтаксиса |
| 2 | Решить 1-3 небольших задания | Первый рабочий код |
| 3 | Сделать коммит | Зафиксированный прогресс |
| 4 | Попросить ревью | Замечания по ошибкам, стилю и C++-мышлению |
| 5 | Исправить замечания | Более качественное решение |
| 6 | Сделать финальный коммит | Завершенная тема или подэтап |
| 7 | Записать итоги | Понятно, что повторить дальше |

## Рекомендуемая структура темы

Для новых уроков лучше придерживаться одинаковой структуры:

```text
lessons/NN_topic/
├── notes.md
├── checklist.md
└── src/
    ├── task01.cpp
    ├── task02.cpp
    └── task03.cpp
```

Файлы:

- `notes.md` — краткая теория и примеры;
- `checklist.md` — список навыков, которые нужно закрепить;
- `src/taskNN.cpp` — практические задания.

Для крупных работ лучше использовать отдельную папку:

```text
projects/
└── NN_project_name/
```

## Как использовать git

Git стоит использовать как журнал обучения и инструмент ревью, а не только как способ сохранить код.

### Перед началом темы

Проверь состояние рабочей директории:

```powershell
git status
```

Если есть незавершенные изменения, лучше сначала понять, к какой теме они относятся.

Создай отдельную ветку:

```powershell
git checkout -b lesson/NN-topic-name
```

Примеры имен:

```text
lesson/02-types
lesson/06-references-const
lesson/15-stl-containers
project/01-calculator
```

### Во время работы

Коммиты должны быть небольшими и понятными.

Хорошие примеры:

```text
lesson 02: add type examples
lesson 02: implement input validation task
lesson 02: fix review comments
project calculator: add operation dispatch
```

Плохие примеры:

```text
update
fix
changes
final
```

Перед коммитом полезно посмотреть изменения:

```powershell
git status
git diff
```

Затем сохранить результат:

```powershell
git add lessons/NN_topic
git commit -m "lesson NN: complete task01"
```

## Как просить ревью

После первого рабочего решения попроси ревью коротко и конкретно.

Примеры:

```text
Проверь lesson/02-types, особенно task02 с вводом.
```

```text
Сделай ревью текущей ветки как репетитор: ошибки, стиль, что стоит повторить.
```

```text
Посмотри diff последнего коммита и скажи, можно ли считать тему закрытой.
```

Во время ревью я буду смотреть:

- собирается ли код;
- есть ли ошибки поведения;
- понятны ли имена и структура;
- нет ли преждевременных усложнений;
- используются ли изучаемые конструкции;
- можно ли объяснить решение своими словами.

## Когда тема считается пройденной

Тему можно считать пройденной, если:

- код собирается;
- задания работают на нескольких разных входных данных;
- основные замечания ревью исправлены;
- ты можешь объяснить ключевые решения в коде;
- в `checklist.md` отмечены освоенные пункты;
- в журнале есть короткая запись об итогах.

## Журнал обучения

Для фиксации прогресса стоит завести файл `LEARNING_LOG.md` в корне репозитория.

Пример записи:

```md
## 2026-06-07 — Lesson 06: Templates

Что сделал:
- начал `clamp<T>`;
- разобрал специализацию `clamp<bool>`;
- повторил `if constexpr` и `<type_traits>`.

Что было сложно:
- разница между перегрузкой и специализацией;
- почему шаблоны обычно пишут в `.hpp`.

Что повторить:
- `std::is_same_v`;
- `static_assert`;
- вывод типов шаблона.
```

Запись не должна быть длинной. Ее задача — показать, что было сделано и где еще есть слабые места.

## Роль репетитора

В этом процессе я могу помогать несколькими способами:

- объяснять новую тему перед заданием;
- составлять задания под текущий уровень;
- делать ревью кода;
- давать подсказки без полного решения;
- разбирать ошибки компиляции;
- предлагать мини-проекты;
- помогать привести структуру репозитория в порядок.

Лучший формат запроса:

```text
Я работаю над lesson/NN-topic. Дай задание без готового решения.
```

или:

```text
Я закончил task01. Сделай ревью как репетитор и не исправляй код сам.
```

Если нужна помощь с ошибкой:

```text
Вот ошибка компиляции. Объясни причину и дай подсказку, но не пиши полное решение.
```

## Важное правило

Если цель — научиться, то готовое решение должно быть последним шагом, а не первым.

Предпочтительный порядок помощи:

1. наводящий вопрос;
2. подсказка по направлению;
3. объяснение конкретной ошибки;
4. маленький пример отдельно от задания;
5. полное решение только если тема уже разобрана или ты явно просишь его.
